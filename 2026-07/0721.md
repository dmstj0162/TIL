2. RAG란?

RAG는 Retrieval-Augmented Generation의 약자다.

한국어로는 보통 검색 증강 생성이라고 한다.

일반적인 LLM은 학습된 정보만 이용해 답변하지만, RAG는 답변 전에 외부 문서에서 관련 내용을 검색한 뒤 그 결과를 LLM에 전달한다.

기본 흐름은 다음과 같다.

사용자 질문
↓
질문과 관련된 문서 검색
↓
관련 chunk 추출
↓
검색 결과를 Context로 구성
↓
질문과 Context를 LLM에 전달
↓
문서 근거 기반 답변 생성

RAG를 사용하는 이유는 다음과 같다.

LLM이 알지 못하는 최신 정보 제공

회사 내부 문서나 개인 문서 활용

근거가 있는 답변 생성

환각 현상 감소

출처 표시 가능

여러 실습 파일에서 공통으로 사용하는 RAG 핵심 기능을 모아둔 파일이다.

주요 역할

chunk 생성

텍스트 벡터화

검색 인덱스 생성

STOPWORDS

질문의 핵심 의미를 구분하는 데 도움이 적은 조사나 자주 쓰는 표현을 제거하기 위한 집합이다.

예시:

STOPWORDS = {
"은", "는", "이", "가", "을", "를",
"무엇", "왜", "알려줘", "알려주세요"
}

이런 단어를 제외하면 질문에서 중요한 단어를 중심으로 비교할 수 있다.

load_documents()

지정한 폴더의 .txt 파일을 읽어 문서 목록으로 만든다.

문서 하나는 다음과 같은 Dictionary 형태다.

{
"source": "center_policy.txt",
"text": "문서 전체 내용"
}

source는 출처 파일명이고, text는 실제 문서 내용이다.

split_sentences()

긴 문자열을 문장 단위로 나눈다.

구분 기준:

마침표

물음표

느낌표

줄바꿈

문장을 먼저 나눈 뒤 여러 문장을 묶어 chunk를 생성한다.

split_text()

긴 문서를 여러 개의 작은 chunk로 나눈다.

주요 매개변수:

chunk_size
overlap_sentences

chunk_size

한 chunk에 들어갈 최대 글자 수를 의미한다.

크기가 너무 작으면 문맥이 잘릴 수 있고, 너무 크면 검색 정확도가 떨어질 수 있다.

overlap_sentences

이전 chunk의 마지막 문장을 다음 chunk에도 일부 포함시키는 설정이다.

예시:

Chunk 1: 문장 A + 문장 B
Chunk 2: 문장 B + 문장 C

문장 B가 겹쳐 들어가기 때문에 chunk 경계에서 문맥이 끊기는 문제를 줄일 수 있다.

벡터화

텍스트를 숫자 형태로 변환한다.

규칙 기반 실습에서는 단어가 몇 번 등장했는지를 Counter로 계산해 문장을 벡터처럼 표현한다.

예시:

"수강 취소 환불 규정"

벡터 형태:

{
"수강": 1,
"취소": 1,
"환불": 1,
"규정": 1
}

코사인 유사도

두 벡터의 방향이 얼마나 비슷한지 계산한다.

결과 범위는 일반적으로 다음과 같다.

1에 가까움 → 매우 유사
0에 가까움 → 관련성이 낮음

RAG에서는 질문 벡터와 각 chunk 벡터의 코사인 유사도를 계산하여 관련 문서를 찾는다.

build_index()

모든 문서를 chunk로 나누고 각 chunk를 벡터화하여 검색 가능한 인덱스를 만든다.

각 검색 항목에는 다음 정보가 들어갈 수 있다.

{
"source": "파일명",
"chunk_number": 1,
"text": "chunk 내용",
"vector": "벡터"
}

retrieve()

질문을 벡터화한 뒤 각 chunk와 유사도를 계산한다.

점수가 높은 순서대로 정렬하여 상위 top_k개를 반환한다.

예시:

results = retrieve(index, question, top_k=3)

format_context()

검색 결과를 LLM 프롬프트에 넣기 좋은 문자열로 변환한다.

예시:

[center_policy.txt #1]
수업 시작 24시간 전까지 취소하면 전액 환불됩니다.

이렇게 출처와 chunk 내용을 함께 제공하면 LLM이 문서에 근거해 답변할 수 있다.

01_no_rag_vs_rag.py

RAG를 사용하지 않은 일반 LLM 답변과 RAG를 사용한 답변을 비교한다.

기본 질문

수업 시작 24시간 이내에 취소하면 얼마나 환불되나요?

일반 프롬프트

다음 질문에 아는 내용을 사용해 답하세요.

이 방식은 모델이 학습된 지식이나 추측을 사용해 답할 수 있다.

RAG 프롬프트

RAG 프롬프트에는 다음 지시사항이 포함된다.

Context에 있는 내용만 사용한다.
근거가 없으면 관련 근거를 찾을 수 없다고 답한다.
답변 마지막에 출처 파일명을 표시한다.

실행 과정

1. data 폴더 문서 로드
2. 문서를 chunk로 분할
3. 인덱스 생성
4. 질문과 관련된 상위 3개 chunk 검색
5. 검색 결과를 Context로 변환
6. 일반 프롬프트와 RAG 프롬프트 생성
7. 두 답변 비교

학습 포인트

첫 번째 문장은 질문과 같은 단어가 많이 들어 있어 높은 점수가 나온다.

두 번째 문장은 주제가 달라 낮은 점수가 나온다.

세 번째 문장은 의미는 비슷하지만 사용한 단어가 다르기 때문에 단순 단어 기반 벡터화에서는 낮은 점수가 나올 수 있다.

이 실습을 통해 규칙 기반 벡터 검색의 한계를 확인할 수 있다.

테스트 데이터

평가 지표: Hit@k

상위 k개의 검색 결과 안에 정답 문서가 포함되었는지 확인한다.

예시:

Hit@1: 6/8 = 75%

의미:

8개의 질문 중 6개는 첫 번째 검색 결과에 정답 문서가 포함되었다.

평가 과정

2. 모든 테스트 질문 실행

4. 기대한 출처가 포함되어 있는지 판단

Embedding을 사용하는 이유

단순 단어 기반 검색은 표현이 다르면 같은 의미를 찾기 어렵다.

예시:

질문: 강의를 포기하면 돈을 돌려받을 수 있나요?
문서: 수강 취소 시 환불이 가능합니다.

단어는 다르지만 의미는 비슷하다.

Embedding은 문장의 의미를 벡터로 표현하기 때문에 동의어나 유사 표현도 찾을 가능성이 높다.

6. RAG 전체 처리 과정

1. 문서 파일 읽기

1. 질문을 벡터로 변환
1. 질문과 각 chunk의 유사도 계산

1. 질문과 Context를 LLM에 전달
1. 문서 근거 기반 답변 생성

1. 핵심 용어 정리

Loader

외부 문서나 파일을 읽어 프로그램에서 사용할 수 있는 형태로 변환하는 구성요소다.

이 실습에서는 .txt 파일을 읽어 Dictionary 목록으로 변환한다.

Document

문서 내용과 metadata를 함께 가진 데이터 단위다.

{
"source": "course_guide.txt",
"text": "문서 내용"
}

Text Splitter

긴 문서를 여러 개의 작은 chunk로 나누는 구성요소다.

Chunk

검색과 LLM 입력에 사용하는 작은 문서 조각이다.

Chunk Size

한 chunk에 들어가는 최대 데이터 크기다.

Chunk Overlap

서로 인접한 chunk가 일부 문장이나 글자를 공유하도록 만드는 설정이다.

Embedding

문장이나 문서의 의미를 숫자 배열로 변환한 값이다.

Vector

Embedding으로 생성된 숫자 배열이다.

Cosine Similarity

두 벡터의 방향을 비교하여 유사도를 계산하는 방법이다.

Retriever

질문과 가장 관련된 문서 또는 chunk를 검색하는 구성요소다.

Top K

검색 결과 중 점수가 높은 상위 몇 개를 가져올지 정하는 값이다.

Context

검색된 문서를 LLM에 전달하기 위해 정리한 근거 정보다.

Hit@k

상위 k개의 검색 결과에 정답 문서가 포함되었는지 평가하는 지표다.

9. 핵심 정리

RAG는 질문과 관련된 문서를 먼저 검색한 뒤 LLM이 답변하도록 만드는 방식이다.

Loader는 문서를 읽고, Text Splitter는 문서를 chunk로 나눈다.

문서에는 내용뿐 아니라 출처 metadata도 함께 저장해야 한다.

chunk가 너무 작으면 문맥이 끊기고, 너무 크면 검색 정확도가 낮아질 수 있다.

chunk overlap은 chunk 경계에서 문맥이 끊기는 문제를 줄인다.

코사인 유사도는 질문과 문서 벡터가 얼마나 유사한지 계산한다.

단순 단어 기반 벡터화는 같은 의미를 다른 단어로 표현하면 찾기 어렵다.

Embedding은 문장의 의미를 벡터로 만들어 유사 표현 검색에 더 적합하다.

검색 품질은 chunk size, overlap, top_k에 따라 달라진다.

Hit@k를 이용하면 검색 설정의 성능을 비교할 수 있다.

최종 RAG 프롬프트에는 검색된 Context와 출처를 함께 전달하는 것이 좋다.
