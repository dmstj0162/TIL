# WebSocket

: 기존 HTTP는 클라이언트가 요청을 보내면 서버가 응답을 하고 연결이 종료되는 방식

: 그래서 실시간 데이터가 필요하면 계속해서 서버에게 반복 요청이 필요함

→ WebSocket은 처음 한 번만 연결을 맺으면 연결을 계속 유지할 수 있음

→ 그래서 클라이언트가 요청하지 않아도 서버가 필요할 때 바로 데이터를 보낼 수 있다. 즉, 서버와 클라이언트가 서로 자유롭게 데이터를 주고 받는 양방향 통신 방식

실제로 Candle 플젝에서는 실시간으로 주식 시세를 가져오는 기능이 있다.

1. Open API가 market-service로 시세를 보내고
2. market-service는
   1. TimescaleDB에 실시간 시세를 발행
   2. Redis Pub/Sub을 구독하고 있는 모든 BFF 인스턴스가 그 데이터를 받은 뒤
   3. WebSocket을 통해 사용자 브라우저로 즉시 전달

여기서 Redis Pub/Sub은 실시간 방송 역할을 함

market-service가 “삼성전자 350,000원” 이라는 메시지를 발행하면

구독중인 모든 BFF가 동시에 그 메시지를 받음

그리고 각 BFF가 자신과 연결된 사용자들에게 WebSocket으로 전달함

즉, Redis는 서버들끼리 실시간으로 데이터를 공유하고, WebSocket은 서버와 사용자 사이를 실시간으로 연결하는 역할을 함

## WebSocket 장점

1. 실시간 통신 가능
2. HTTP처럼 요청을 계속 보내지 않아도 되기 때문에 불필요한 트래픽이 줄어듦
3. 서버가 즉시 데이터를 보낼 수 있어서 주식 시세나 채팅처럼 실시간 서비스에 적합

## WebSocket 단점

1. 연결을 계속 유지하기 때문에 자원 사용
2. 연결이 끊어지면 재연결 처리 필요
3. 사용자가 많아질수록 연결 수가 증가하기 때문에 서버에서도 연결을 효율적으로 관리해야 함

   → 그래서 BFF를 여러개 띄우고 Redis Pub/Sub으로 데이터를 공유하면 어느 BFF에 연결되어 있든 동일한 실시간 시세를 받을 수 있음

### WebSocket만 쓰지 않고 Redis Pub/Sub을 쓰는 이유?

- WebSocket은 서버와 사용자 간의 실시간 통신을 담당하지만, 서버가 여러대일 경우 각 서버가 동일한 실시간 데이터를 받아야 함. Redis Pub/Sub은 그 데이터를 모든 서버에 동시에 전달해주기 때문에 여러 대의 BFF가 있어도 모든 사용자가 동일한 실시간 시세를 받을 수 있음

## STOMP

: 메시지를 어떻게 보낼지 규칙을 정한 프로토콜

: @MessageMapping

- WebSocket 위에서 메시지를 주고받는 규칙을 정해주는 프로토콜
- 실시간 시세는 순수 WebSocket으로도 구현할 수 있지만, 사용자가 특정 종목을 구독하고 해당 종목의 시세만 받는 구조라면 STOMP를 사용하는 것이 더 편리함
